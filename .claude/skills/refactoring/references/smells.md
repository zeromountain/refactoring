# 코드에서 나는 악취 (3장) + 악취 제거 기법 표 (부록 B)

출처: 『리팩터링 2판』 3장 (Martin Fowler · Kent Beck). 각 악취의 **처방(→)** 은
3장 본문이 실제로 참조하는 기법만 나열했다(부록 B와 동일). 기법 이름 뒤 번호는 이 스킬의
카탈로그 절 번호다(`catalog-*.md`).

> "냄새가 나면 바꿔라." — Grandma Beck
> 악취는 "반드시 고쳐야 할 것"이 아니라 "살펴볼 가치가 있다는 신호"다. 판단은 사람이 한다.

## 진단 순서 (AI 에이전트용)
1. 코드를 읽으며 아래 24개 악취 중 무엇이 **가장 강하게** 나는지 1~3개 고른다.
2. 각 악취의 처방 목록에서 **가장 작은 단계로 시작할 수 있는** 기법을 고른다(보통 함수 추출·이름 바꾸기·문장 슬라이드).
3. 약한 악취(상속 포기, 주석, 반복문 등)는 문제를 일으키고 있을 때만 손댄다.

---

## 3.1 기이한 이름 (Mysterious Name)
- 이름만 봐서는 무엇을 하는지, 어떻게 써야 하는지 알 수 없는 함수·변수·필드·클래스.
- 이름 짓기는 가장 흔하고 가장 중요한 리팩터링. 좋은 이름이 떠오르지 않으면 설계에 더 깊은 문제가 있다는 신호일 때가 많다.
- → 함수 선언 바꾸기(6.5), 변수 이름 바꾸기(6.7), 필드 이름 바꾸기(9.2)

## 3.2 중복 코드 (Duplicated Code)
- 같은 코드 구조가 두 곳 이상. 읽을 때마다 "정말 같은가?" 비교해야 하고, 고칠 때마다 전부 찾아야 한다.
- 같은 클래스의 두 메서드에 같은 표현식 → 추출해 양쪽에서 호출. 비슷하지만 다르면 먼저 문장을 모아 추출 가능하게. 형제 서브클래스에 중복이면 위로 올린다.
- → 함수 추출하기(6.1), 문장 슬라이드하기(8.6), 메서드 올리기(12.1)

## 3.3 긴 함수 (Long Function)
- 짧은 함수로 이뤄진 프로그램이 오래 산다. 핵심은 **길이가 아니라 "무엇을 하는가"와 "어떻게 하는가" 사이의 의미적 거리**다.
- 휴리스틱: **주석을 달고 싶으면 함수를 만든다.** 한 줄이라도 설명이 필요하면 추출한다. 함수 이름이 의도를 말하면 본문을 볼 필요가 없다.
- 추출 대상 찾기: 주석 블록, 조건문, 반복문, switch의 각 분기. 반복문에 이름 붙이기 어려우면 두 가지 일을 하는 것 → 반복문 쪼개기.
- 매개변수·임시 변수가 많아 추출이 어려우면: 임시 변수를 질의로, 매개변수 객체, 객체 통째로 넘기기. 그래도 안 되면 최후 수단으로 함수를 명령으로.
- → 함수 추출하기(6.1), 임시 변수를 질의 함수로 바꾸기(7.4), 매개변수 객체 만들기(6.8), 객체 통째로 넘기기(11.4), 함수를 명령으로 바꾸기(11.9), 조건문 분해하기(10.1), 조건부 로직을 다형성으로 바꾸기(10.4), 반복문 쪼개기(8.7)

## 3.4 긴 매개변수 목록 (Long Parameter List)
- 매개변수 하나로 다른 매개변수를 얻을 수 있으면 제거. 자료구조에서 값을 뽑아 넘기고 있으면 통째로. 항상 함께 다니는 매개변수는 객체로. 플래그 인수는 제거.
- 여러 함수가 같은 매개변수들을 공유하면 클래스로 묶어 필드로 만든다(부분 적용 함수의 OOP 버전).
- → 매개변수를 질의 함수로 바꾸기(11.5), 객체 통째로 넘기기(11.4), 매개변수 객체 만들기(6.8), 플래그 인수 제거하기(11.3), 여러 함수를 클래스로 묶기(6.9)

## 3.5 전역 데이터 (Global Data)
- 어디서든 수정될 수 있고 누가 건드렸는지 추적할 수 없다. 전역 변수뿐 아니라 클래스 변수·싱글턴도 해당.
- 첫 수는 항상 **캡슐화**: 함수로 감싸면 수정 지점이 보이고 접근을 통제할 수 있다. 그다음 스코프를 최대한 좁힌다.
- 파라켈수스의 격언: 독과 약의 차이는 용량이다. 조금은 괜찮지만 많아질수록 기하급수적으로 어려워진다.
- → 변수 캡슐화하기(6.6)

## 3.6 가변 데이터 (Mutable Data)
- 한 곳에서 바꾼 데이터가 다른 곳의 기대를 깨뜨린다. 드물게만 발생하면 찾기 매우 어렵다.
- 스코프가 몇 줄뿐이면 문제 없다. 스코프가 넓어질수록 위험이 커진다.
- 처방: 갱신을 좁은 함수로 모으고(캡슐화), 용도별로 변수 분리, 부수효과 없는 코드와 갱신 코드를 분리, API에서 질의/변경 분리, 세터 제거, 계산 가능한 값은 저장하지 말고 계산, 내부 구조가 있는 값은 제자리 수정 대신 통째로 교체.
- → 변수 캡슐화하기(6.6), 변수 쪼개기(9.1), 문장 슬라이드하기(8.6), 함수 추출하기(6.1), 질의 함수와 변경 함수 분리하기(11.1), 세터 제거하기(11.7), 파생 변수를 질의 함수로 바꾸기(9.3), 여러 함수를 클래스로 묶기(6.9), 여러 함수를 변환 함수로 묶기(6.10), 참조를 값으로 바꾸기(9.4)

## 3.7 뒤엉킨 변경 (Divergent Change)
- **한 모듈**이 서로 다른 이유로 여러 방식으로 자주 변경된다. "DB가 바뀌면 이 세 함수, 금융 상품이 추가되면 이 네 함수." → 맥락이 다르니 모듈을 나눈다.
- 두 맥락이 순차적이면(가져온 뒤 처리) 단계 쪼개기로 중간 자료구조를 둔다. 호출이 얽혀 있으면 모듈을 만들고 함수를 옮긴다. 한 함수 안에 섞여 있으면 먼저 추출한다.
- → 단계 쪼개기(6.11), 함수 옮기기(8.1), 함수 추출하기(6.1), 클래스 추출하기(7.5)

## 3.8 산탄총 수술 (Shotgun Surgery)
- 뒤엉킨 변경의 반대. **한 가지 변경**을 위해 여러 모듈을 조금씩 고쳐야 한다. 놓치기 쉽다.
- 흩어진 로직을 한 모듈로 모은다. 비슷한 데이터를 다루는 함수들은 클래스로, 자료구조를 변환·보강하는 함수들은 변환 함수로. 인라인으로 일단 한데 모은 뒤(중간 단계로 큰 함수·클래스가 생겨도 괜찮다) 다시 적절히 추출한다.
- → 함수 옮기기(8.1), 필드 옮기기(8.2), 여러 함수를 클래스로 묶기(6.9), 여러 함수를 변환 함수로 묶기(6.10), 단계 쪼개기(6.11), 함수 인라인하기(6.2), 클래스 인라인하기(7.6)

## 3.9 기능 편애 (Feature Envy)
- 함수가 자기 모듈보다 **다른 모듈의 데이터·함수**와 더 많이 소통한다. 다른 객체의 게터를 대여섯 개 호출해 값을 계산하는 함수가 전형.
- 함수는 데이터 곁에 있고 싶어 한다 → 옮긴다. 일부만 편애하면 그 부분만 추출해 옮긴다. 여러 모듈을 쓰면 **데이터가 가장 많은 곳**으로.
- 예외: 전략(Strategy)·방문자(Visitor)·자기 위임(Self Delegation) 패턴은 일부러 이 규칙을 깬다(뒤엉킨 변경 대응). 근본 원칙은 "함께 변하는 것은 함께 둔다."
- → 함수 옮기기(8.1), 함수 추출하기(6.1)

## 3.10 데이터 뭉치 (Data Clumps)
- 서너 개 데이터가 항상 같이 다닌다(여러 클래스의 필드로, 여러 함수의 매개변수로).
- 먼저 필드로 나타난 곳에 클래스 추출, 그다음 시그니처를 매개변수 객체·통째로 넘기기로 줄인다.
- 테스트: 값 하나를 지워도 나머지가 의미 있는가? 없다면 객체가 태어나고 싶어 하는 것.
- 레코드가 아니라 **클래스**로 만들면 기능 편애하던 동작이 옮겨 와 좋은 향기(클래스)가 된다.
- → 클래스 추출하기(7.5), 매개변수 객체 만들기(6.8), 객체 통째로 넘기기(11.4)

## 3.11 기본형 집착 (Primitive Obsession)
- 돈·좌표·범위·전화번호 같은 도메인 개념을 int·string으로 다룬다("stringly typed"). 단위 없는 물리량 계산, `a < upper && a > lower` 남발.
- 의미 있는 타입은 표시 로직까지 일관되게 담을 수 있다.
- 타입 코드가 조건부 동작을 제어하면 서브클래스 → 다형성. 함께 다니는 기본형 묶음은 데이터 뭉치로 다룬다.
- → 기본형을 객체로 바꾸기(7.3), 타입 코드를 서브클래스로 바꾸기(12.6), 조건부 로직을 다형성으로 바꾸기(10.4), 클래스 추출하기(7.5), 매개변수 객체 만들기(6.8)

## 3.12 반복되는 switch문 (Repeated Switches)
- switch 자체는 악취가 아니다(1판의 "switch문"에서 이름이 바뀐 이유). 문제는 **같은 조건 분기가 여러 곳에 반복**되는 것 — 분기를 하나 추가하려면 전부 찾아 고쳐야 한다.
- → 조건부 로직을 다형성으로 바꾸기(10.4)

## 3.13 반복문 (Loops)
- 일급 함수가 있는 언어에서는 filter/map 같은 파이프라인이 "무엇을 골라 무엇을 하는지" 훨씬 명확하다.
- → 반복문을 파이프라인으로 바꾸기(8.8)

## 3.14 성의 없는 요소 (Lazy Element)
- 본문과 이름이 같은 함수, 사실상 함수 하나인 클래스. 나중에 커질 줄 알았지만 그러지 못했거나, 리팩터링으로 쪼그라든 것.
- 품위 있게 죽여 준다.
- → 함수 인라인하기(6.2), 클래스 인라인하기(7.6), 계층 합치기(12.9)

## 3.15 추측성 일반화 (Speculative Generality)
- "언젠가 필요할 거야"로 넣은 훅, 추상 클래스, 미사용 매개변수. 쓰이면 가치 있지만 안 쓰이면 방해만 된다(YAGNI 위반).
- 테스트 코드만 쓰는 함수·클래스가 있으면 테스트와 함께 지운다.
- → 계층 합치기(12.9), 함수 인라인하기(6.2), 클래스 인라인하기(7.6), 함수 선언 바꾸기(6.5, 매개변수 제거), 죽은 코드 제거하기(8.9)

## 3.16 임시 필드 (Temporary Field)
- 특정 상황에서만 값이 설정되는 필드. 객체는 모든 필드를 항상 필요로 한다고 기대하기 때문에 이해가 어렵다.
- 고아 필드들에게 집(클래스)을 만들어 주고 관련 코드를 옮긴다. 필드가 유효하지 않을 때를 위한 특이 케이스 클래스로 조건문을 없앨 수도 있다.
- → 클래스 추출하기(7.5), 함수 옮기기(8.1), 특이 케이스 추가하기(10.5)

## 3.17 메시지 체인 (Message Chains)
- `a.getB().getC().getD()` — 클라이언트가 탐색 구조에 결합된다. 중간 관계가 바뀌면 클라이언트도 바뀐다.
- 위임 숨기기는 체인의 어느 지점에나 적용 가능하지만, 전부 하면 중간 객체가 모두 중개자가 된다. 더 나은 대안: 결과 객체를 **어디에 쓰는지** 보고, 그 코드를 추출해 체인 아래로 옮긴다.
- 여러 클라이언트가 같은 경로를 탐색하면 그 경로를 메서드로 제공한다. 짧은 체인은 괜찮다.
- → 위임 숨기기(7.7), 함수 추출하기(6.1), 함수 옮기기(8.1)

## 3.18 중개자 (Middle Man)
- 클래스 메서드의 절반이 다른 클래스로 위임만 한다. 캡슐화가 지나친 상태.
- 몇 개만 그렇다면 인라인. 추가 동작이 있으면 위임 관계를 상속 관계로 접거나(반대로) 편다.
- → 중개자 제거하기(7.8), 함수 인라인하기(6.2), 슈퍼클래스를 위임으로 바꾸기(12.11), 서브클래스를 위임으로 바꾸기(12.10)

## 3.19 내부자 거래 (Insider Trading)
- 모듈끼리 뒷거래(서로의 내부 데이터를 과하게 주고받음). 상속은 흔히 공모를 낳는다 — 서브클래스는 부모가 원하는 것보다 더 많이 안다.
- 함수·필드를 옮겨 수다를 줄이고, 공통 관심사는 제3의 모듈로 빼거나 중개 역할을 시킨다. 상속에서 독립할 때가 됐으면 위임으로 바꾼다.
- → 함수 옮기기(8.1), 필드 옮기기(8.2), 위임 숨기기(7.7), 서브클래스를 위임으로 바꾸기(12.10), 슈퍼클래스를 위임으로 바꾸기(12.11)

## 3.20 거대한 클래스 (Large Class)
- 필드가 너무 많으면 중복 코드가 멀지 않다. 공통 접두사·접미사를 가진 필드 묶음이 컴포넌트 후보(`depositAmount`, `depositCurrency`).
- 클라이언트가 클래스 기능의 **부분집합**만 쓴다면 그 부분집합이 분리 후보. 500줄 메서드 다섯 개 → 10줄 메서드 다섯 개 + 2줄 메서드 열 개.
- → 클래스 추출하기(7.5), 슈퍼클래스 추출하기(12.8), 타입 코드를 서브클래스로 바꾸기(12.6)

## 3.21 서로 다른 인터페이스의 대안 클래스들 (Alternative Classes with Different Interfaces)
- 서로 대체 가능해야 할 클래스들의 인터페이스가 다르다. 시그니처를 맞추고, 프로토콜이 일치할 때까지 동작을 옮기고, 중복이 생기면 슈퍼클래스로.
- → 함수 선언 바꾸기(6.5), 함수 옮기기(8.1), 슈퍼클래스 추출하기(12.8)

## 3.22 데이터 클래스 (Data Class)
- 필드 + 게터/세터뿐인 클래스. 다른 클래스가 너무 세세하게 조작한다 = **동작이 잘못된 곳에 있다**는 신호.
- public 필드면 즉시 레코드 캡슐화. 바뀌면 안 되는 필드는 세터 제거. 게터/세터를 쓰는 클라이언트의 동작을 데이터 클래스 안으로 옮긴다.
- 예외: 단계 쪼개기의 중간 자료구조처럼 함수 호출의 **결과 레코드**(사실상 불변)는 캡슐화할 필요 없다.
- → 레코드 캡슐화하기(7.1), 세터 제거하기(11.7), 함수 옮기기(8.1), 함수 추출하기(6.1), 단계 쪼개기(6.11)

## 3.23 상속 포기 (Refused Bequest)
- 서브클래스가 부모의 메서드·데이터 중 일부만 쓴다. 전통적 처방은 형제 클래스를 만들어 안 쓰는 것을 내리는 것.
- 하지만 열에 아홉은 냄새가 약해 손볼 가치가 없다. **구현**을 거부하는 건 괜찮다. **인터페이스**를 거부한다면 강한 악취 → 계층을 만지지 말고 위임으로 바꾼다.
- → 메서드 내리기(12.4), 필드 내리기(12.5), 서브클래스를 위임으로 바꾸기(12.10), 슈퍼클래스를 위임으로 바꾸기(12.11)

## 3.24 주석 (Comments)
- 주석 자체는 좋은 향기다. 문제는 주석이 **탈취제**로 쓰일 때 — 두꺼운 주석은 대개 나쁜 코드를 가리고 있다.
- 블록이 무엇을 하는지 설명하려면 추출. 추출했는데도 설명이 필요하면 이름을 바꾼다. 시스템 상태 규칙이면 어서션.
- 좋은 주석: **왜** 했는지, 무엇을 모르는지(확신 없는 부분).
- → 함수 추출하기(6.1), 함수 선언 바꾸기(6.5), 어서션 추가하기(10.6)
