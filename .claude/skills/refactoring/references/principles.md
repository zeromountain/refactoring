## 2장 리팩터링 원칙

### 2.1 리팩터링 정의
- **명사**: 소프트웨어의 겉보기 동작은 그대로 유지한 채, 코드를 이해하고 수정하기 쉽도록 내부 구조를 변경하는 기법.
- **동사**: 그런 리팩터링 기법을 연달아 적용해서 겉보기 동작은 유지한 채 소프트웨어를 재구성하다.
- 핵심은 **작은 단계**다. 각 단계는 그 자체로 동작을 보존하며, 언제든 멈춰도 코드가 정상 동작해야 한다.
  며칠씩 시스템이 깨진 채로 "리팩터링 중"이라면 그것은 리팩터링이 아니라 **재구성(restructuring)** 이다.
- **겉보기 동작(observable behavior)**: 사용자·호출자가 관찰하는 동작. 리팩터링 전후로 동일한 입력에 동일한 결과를 내야 한다.
  단, 이미 있던 버그를 그대로 두는 것은 허용된다(버그 수정은 다른 모자).
- 성능은 겉보기 동작에 포함하지 않는다(리팩터링으로 느려질 수 있고, 그건 나중에 다룬다 → 2.8).

### 2.2 두 개의 모자 (Two Hats, Kent Beck)
- **기능 추가 모자**: 기존 코드를 건드리지 않고 새 기능을 추가한다. 테스트를 추가하고 통과시킨다.
- **리팩터링 모자**: 기능을 추가하지 않는다. 코드 재구성만 한다. 테스트도 (인터페이스가 바뀌지 않는 한) 추가하지 않는다.
- 작업 중 두 모자를 자주 바꿔 쓰되, **동시에 쓰지 않는다**. 지금 어떤 모자를 쓰고 있는지 항상 인식하라.
- 실전 규칙: 한 커밋(또는 한 단계)에는 리팩터링 **또는** 동작 변경 중 하나만 담는다.

### 2.3 리팩터링하는 이유
1. **설계가 좋아진다** — 리팩터링 없이 코드는 부패한다. 중복을 제거하면 "모든 코드가 언제나 한 번만 말한다".
2. **이해하기 쉬워진다** — 코드는 미래의 나(또는 동료)에게 쓰는 글이다. 이해한 내용을 코드에 반영하면 잊더라도 코드가 기억한다.
3. **버그를 찾기 쉬워진다** — 구조가 명확해지면 가정이 드러나고, 버그가 숨을 곳이 줄어든다.
4. **더 빨리 개발할 수 있다** — 설계 지구력 가설(Design Stamina Hypothesis): 내부 품질에 투자하면 기능 추가 속도가 시간이 지나도 유지된다. 좋은 설계가 없으면 처음엔 빠르지만 곧 정체된다.

### 2.4 언제 리팩터링해야 할까?
- **삼진 규칙(Rule of Three, Don Roberts)**: 처음엔 그냥 한다. 비슷한 일을 두 번째로 하면 중복이라 생각하되 참는다. 세 번째로 하면 리팩터링한다.
- **준비를 위한 리팩터링(preparatory)**: 기능을 추가하거나 버그를 고치기 직전, 그 작업이 쉬워지도록 코드를 먼저 정리한다. "새 기능을 넣기 좋은 구조로 바꾼 다음 기능을 넣는다."
- **이해를 위한 리팩터링(comprehension)**: 코드를 읽으면서 파악한 의도를 이름·구조로 코드에 새긴다. 이해가 코드에 남는다.
- **쓰레기 줍기 리팩터링(litter-pickup)**: 지나가다 본 사소한 지저분함을 곧바로 치운다. 캠핑 규칙: "처음 왔을 때보다 깨끗하게 하고 떠난다."
- **계획된 리팩터링 vs 수시로 하는 리팩터링**: 대부분의 리팩터링은 따로 일정을 잡지 않고 **다른 작업의 일부로 수시로(opportunistic)** 이뤄져야 한다. 별도 리팩터링 일정은 보통 그동안 방치한 결과다.
- **오래 걸리는 리팩터링**: 팀 전체가 몇 주에 걸쳐 조금씩. 브랜치를 분리해 한 번에 하지 말고, 매번 조금씩 원하는 방향으로 옮긴다(예: 라이브러리 교체 → 추상 인터페이스 도입 후 점진 이전).
- **코드 리뷰에 리팩터링 활용**: 리뷰어와 함께 앉아 리팩터링해 보면 제안이 구체화되고 이해가 공유된다(페어 프로그래밍이 자연스러운 형태).
- **관리자에게 어떻게 설명할까?**: 리팩터링을 따로 보고하지 마라. 가장 빠르게 기능을 넣는 방법이 리팩터링이면 그냥 그렇게 하라.
- **리팩터링하지 말아야 할 때**
  - 굳이 수정할 필요 없고, 외부 API처럼 다룰 수 있는 지저분한 코드는 그대로 둔다.
  - 처음부터 새로 짜는 게 쉬운 경우. 이 판단은 어렵고 경험이 필요하다.

### 2.5 리팩터링 시 고려할 문제
- **새 기능 개발 속도 저하** — 리팩터링의 목적은 개발 속도다. 크게 도움 안 되는 부분을 지금 손볼 필요는 없다. 반대로 "리팩터링을 너무 많이 하는" 경우보다 "너무 적게 하는" 경우가 훨씬 흔하다.
- **코드 소유권** — 강한 개인 소유권은 함수 이름 바꾸기조차 막는다. 팀 단위 소유(누구나 어디든 수정)를 권장. 외부 공개 API는 옛 인터페이스를 유지하고 새 것으로 위임(deprecate).
- **브랜치** — 장기 기능 브랜치는 통합 시 리팩터링 충돌을 키운다. **지속적 통합(CI, 트렁크 기반 개발)** 을 권장: 최소 하루 한 번 메인에 통합.
- **테스트** — 리팩터링의 안전망은 자가 테스트 코드다. 테스트가 없으면 먼저 테스트를 마련한다(4장). 리팩터링 도구가 보장하는 안전한 리팩터링은 예외.
- **레거시 코드** — 테스트 없는 대형 레거시는 어렵다. Feathers의 『레거시 코드 활용 전략』대로 **테스트 가능한 접합부(seam)** 를 찾아 테스트를 넣고, 자주 다니는 부분부터 조금씩 개선한다.
- **데이터베이스** — 스키마 변경은 점진적 마이그레이션(Evolutionary Database Design). 여러 릴리스에 걸쳐 병렬 변경(parallel change / expand-contract): 새 필드 추가 → 양쪽 기록 → 읽기 이전 → 옛 필드 제거.

### 2.6 리팩터링, 아키텍처, YAGNI
- 리팩터링 덕분에 아키텍처를 처음에 완벽히 결정할 필요가 없다. **진화하는 아키텍처**.
- **YAGNI (You Aren't Gonna Need It)**: 나중에 필요할 것 같은 유연성(매개변수, 훅, 추상화)을 **미리** 넣지 마라. 실제로 필요해질 때 리팩터링으로 넣는 것이 대개 더 싸다.
  추측성 일반화(3.15)는 YAGNI 위반의 결과다.
- 단, YAGNI는 리팩터링·지속적 설계와 **함께** 쓸 때만 성립한다. 내부 품질을 소홀히 하는 핑계로 쓰면 안 된다.
- 지금 넣기 쉽고 나중에 넣기 아주 어려운 유연성이라면 지금 넣는다(가끔 있는 예외).

### 2.7 리팩터링과 소프트웨어 개발 프로세스
- 리팩터링은 XP의 **자가 테스트 코드 · 지속적 통합 · 리팩터링** 세 기둥 중 하나이며, 나머지 둘이 없으면 힘을 못 쓴다.
- 자가 테스트 → 리팩터링 오류를 즉시 감지. CI → 리팩터링이 남의 브랜치와 충돌 없이 전파.
- TDD의 "레드-그린-**리팩터**" 주기가 이 모두를 묶는다.
- 이 셋이 갖춰지면 YAGNI가 성립하고, 지속적 배포(CD)가 가능해진다.

### 2.8 리팩터링과 성능
- "리팩터링하면 느려진다"는 우려에 대한 답: **먼저 이해하기 쉬운 구조로 만든 뒤, 필요하면 최적화**한다.
- 잘 리팩터링된 코드는 성능 개선도 쉽다: 튜닝에 쓸 시간이 늘고, 프로파일러로 핫스팟을 정확히 찾을 수 있다.
- 세 가지 접근: (1) 시간 예산 배분(실시간 시스템에서만), (2) 지속적 관심(대부분 시간 낭비), (3) **성능 튜닝 단계를 두고 프로파일러로 측정해 핫스팟만 최적화**(권장).
- 실제로 성능에 영향을 주는 코드는 극히 일부다. 나머지 90%의 최적화는 낭비다.
- 리팩터링 중 "이건 느려질 것 같다"는 직감이 들면 **무시하고 계속**하되, 나중에 측정한다.

### 2.9 리팩터링의 유래
- 용어 자체의 창시자는 불명. Ward Cunningham·Kent Beck(Smalltalk), Ralph Johnson(일리노이대), Bill Opdyke(박사 논문 1992, 최초의 리팩터링 학술 저술), John Brant·Don Roberts(Refactoring Browser).
- Fowler는 "발명자가 아니라 기록자"임을 강조.

### 2.10 리팩터링 자동화
- IDE(IntelliJ 계열, Eclipse, Visual Studio 등)는 AST 기반으로 **이름 바꾸기, 함수 추출, 변수 인라인** 등을 안전하게 수행. 정적 타입 언어에서 특히 강력.
- 텍스트 검색·치환은 리팩터링이 아니다. 구문 트리를 이해하는 도구를 써라.
- 도구가 지원하는 리팩터링은 테스트가 없어도 비교적 안전하지만, 그 외에는 여전히 테스트가 필요하다.
- AI 에이전트가 리팩터링할 때의 함의: 언어 서버/IDE 리팩터링 명령이 있으면 우선 활용하고, 없으면 **작은 단계 + 매 단계 테스트**로 도구의 역할을 대신한다.

## 4장 테스트 구축하기

### 4.1 자가 테스트 코드의 가치
- **자가 테스트 코드**: 명령 한 번으로 전체 테스트를 실행하고, 통과하면 심각한 결함이 없다고 믿을 수 있는 상태.
- 리팩터링의 필수 전제. 테스트가 리팩터링 실수를 몇 분 안에 알려 주므로 디버깅 시간이 사라진다.
- 테스트를 작성하기 가장 좋은 시점은 **코드를 작성하기 전**(TDD). 인터페이스가 명확해지고 "완료" 기준이 생긴다.
- "모든 테스트는 완벽하게 만들 수 없더라도, 불완전한 테스트라도 작성해 실행하는 게 낫다."

### 4.2 ~ 4.4 테스트 작성 요령 (책의 예제 흐름에서 뽑은 원칙)
- 테스트는 **실패하는지 확인**한다(일부러 코드를 망가뜨려 테스트가 잡아내는지 본다). 실패하지 않는 테스트는 아무것도 검증하지 않는다.
- **자주 실행**한다: 리팩터링 한 단계마다, 최소 몇 분마다. 컴파일 수준으로 가볍게.
- 테스트 하나는 **한 가지**를 검증한다. 실패 메시지만 봐도 무엇이 깨졌는지 알 수 있게 이름을 짓는다.
- 픽스처는 테스트마다 새로 만든다(`beforeEach`). 공유 픽스처는 테스트 간 오염을 만든다(4.5 픽스처 수정하기).
- 픽스처를 수정하는 테스트(setter 호출 → 파생값 확인)도 반드시 포함한다. 읽기 전용 테스트만으론 부족하다.

### 4.6 경계 조건 검사하기
- 정상 경로만 테스트하지 말고 **경계**를 공략한다: 빈 컬렉션, 0, 음수, 최댓값, null/undefined, 잘못된 타입, 존재하지 않는 키.
- "문제가 생길 가능성이 있는 경계 조건을 생각해 보고 그 부분을 집중적으로 테스트한다."
- 프로그램이 잘못된 입력에 어떻게 반응해야 하는지는 설계 결정이다. 어서션(10.6)을 넣거나 예외를 던지는 것도 한 방법.
- 리팩터링에는 기존 동작을 그대로 보존하는 테스트만 있으면 충분하다. 입력 검증 개선은 별도 모자.

### 4.7 끝나지 않은 여정
- 테스트 커버리지는 숫자보다 **"버그를 놓치지 않을 것 같다는 확신"** 이 기준이다.
- 버그를 발견하면 그 버그를 드러내는 테스트부터 작성한다.
- 테스트도 코드다. 리팩터링 대상이며, 너무 많거나 느린 테스트는 정리한다.
- 위험한 부분에 집중: 단순 접근자(getter/setter)까지 테스트할 필요는 없다.

## 5장 리팩터링 카탈로그 보는 법

### 5.1 리팩터링 설명 형식
각 기법은 다음 형식으로 설명된다. 이 스킬의 `catalog-*.md` 파일도 같은 골격을 따른다.
1. **이름** — 어휘를 공유하려면 이름이 중요. 1판 이름(별칭)도 병기.
2. **개요(sketch)** — 전·후 코드 스케치. 한눈에 무슨 기법인지 파악.
3. **배경(motivation)** — 왜 필요한지, 언제 쓰지 말아야 하는지.
4. **절차(mechanics)** — 단계별 수행 방법. 각 단계는 작게, 단계마다 테스트. 익숙해지면 큰 보폭으로.
5. **예시(example)** — 실제 코드 적용.

### 5.2 리팩터링 기법 선정 기준
- 2판은 특정 언어(JavaScript)에 얽매이지 않도록 **일반적으로 유용한** 기법만 수록. 언어 특화·희귀 기법은 제외.
- 1판의 클래스 중심 기법은 **함수 중심**으로 일반화(예: Extract Method → Extract Function, Move Method → Move Function).
- 1판의 여러 기법이 하나로 통합됨(예: Rename Method, Add/Remove Parameter → Change Function Declaration).
