# 리팩터링 (Refactoring, 2nd ed.)

리팩터링 = **겉보기 동작은 그대로 두고** 내부 구조를 이해·수정하기 쉽게 바꾸는 것.
작은 단계를 연달아 적용하고, 매 단계 뒤에 테스트를 돌린다. 며칠씩 깨진 채로 두는 건 리팩터링이 아니다.

## 두 가지 모드 — 요청을 보고 먼저 고른다

| 모드 | 언제 | 하는 일 |
|---|---|---|
| **진단** | "리뷰해줘", "냄새 봐줘", "뭘 고쳐야 해?", "계획 세워줘", 범위가 크거나 불명확할 때 | 코드를 **수정하지 않고** 악취 보고서 + 기법 순서 + 위험을 낸다 (형식은 아래) |
| **적용** | "리팩터링해줘", "이 함수 정리해", 기법 이름을 지목, 진단 후 승인 | 절차대로 한 단계씩 수정·검증·(커밋) |

인수가 주어지면(`/refactoring 진단 src/x.ts`, `/refactoring 적용 7.4 src/x.ts`) `진단|적용 [절번호|기법명] [대상]`으로 읽고 모드를 추론하지 않는다. 인수: `$ARGUMENTS`

범위가 함수~파일 하나이고 처방이 명백하면 바로 적용. 여러 파일·공개 API·상속 계층·스키마가 걸리면 **진단을 먼저 보여 주고** 승인 뒤 적용.

## 지켜야 할 원칙

1. **두 개의 모자** — 리팩터링과 기능 추가를 동시에 하지 않는다. 둘 다 요청받으면 순서를 나누고(리팩터링 → 커밋 → 기능) 그렇게 한다고 말한다.
2. **테스트가 먼저** — 없으면 현재 동작을 고정하는 특성화 테스트부터. 일부러 깨뜨려 정말 잡는지 확인한다.
3. **작은 단계, 매번 검증** — 절차 한 단계 = 테스트·타입체크 한 번. 빨개지면 디버깅하지 말고 되돌려 더 작게.
4. **삼진 규칙** — 세 번째 중복에서 정리한다. 두 번째는 참는다.
5. **YAGNI** — 미래를 위한 유연성을 넣지 않는다. 추측성 일반화는 제거 대상이지 추가 대상이 아니다.
6. **성능은 나중에** — 명확한 구조 먼저. 느려지면 측정해서 핫스팟만.
7. **이름이 최우선** — "어떻게"가 아니라 "무엇을/왜". 좋은 이름이 안 떠오르면 추출하지 않는다.
8. **도구를 쓴다** — 언어 서버의 rename/extract가 있으면 텍스트 치환 대신 그것을.
9. **언어 관용을 따른다** — 책의 JS 예시를 그대로 옮기지 말고 `references/language-notes.md`의 대응표로(Go의 오류 값, Rust의 enum+match, Kotlin sealed class …).

## 적용 절차 (체크리스트)

```
[ ] 0 범위     왜 하는가(준비/이해/쓰레기 줍기/계획)를 한 줄로. 요청 밖 코드는 건드리지 않는다.
[ ] 1 안전망   git status 깨끗 → 커밋 여부 확인(기본: 안 함) → 테스트 명령 확인 → 초록 확인 → 일부러 깨뜨려 빨강 확인 → 되돌림.
              테스트 없음 → references/safety.md 의 특성화 테스트 절차.
[ ] 2 진단     references/smells.md 로 악취 1~3개. 우선순위는 references/judgment.md.
[ ] 3 계획     references/recipes.md 에서 연쇄를 고르고, 각 기법의 절차를 references/catalog-*.md 에서 읽는다.
[ ] 4 실행     절차 한 단계 → 테스트/타입체크 → 초록이면 다음. 기법 하나 = 커밋 하나(사용자가 커밋을 원할 때).
[ ] 5 회색지대 평가 순서·부동소수점·예외 타입·직렬화 이름·공개 API가 걸리면 멈추고 묻는다(safety.md).
[ ] 6 마무리   죽은 코드·불필요해진 주석 제거, 이름 재검토, 전체 테스트, git diff 읽고 "순수 이동이 아닌 줄" 점검.
[ ] 7 보고     아래 형식.
```

도중에 버그를 발견하면 **고치지 말고 기록**한다(다른 모자). 리팩터링을 끝낸 뒤 별도로 알린다.
규모가 한 번에 끝나지 않으면(라이브러리 교체, 전체 이름 변경, 스키마) `references/large-scale.md`의 확장–이전–축소 계획을 먼저 제시한다.

## 진단 보고서 형식

```
### 리팩터링 진단: <대상>
안전망: 테스트 <있음/없음/부분> · 명령 `<cmd>` · 마지막 실행 <초록/빨강>
| # | 악취 | 위치 | 근거 (줄/증상) | 처방 (기법 순서) | 위험 |
| 1 | 반복되는 switch | pricing.ts:40,88 | tier 분기 2곳 | R2: 팩터리 → 서브클래스 → 다형성 | 중 (생성 지점 3곳) |
권장 순서와 이유 · 예상 단계 수(커밋 단위)
손대지 않을 것: <이유와 함께>
확인 필요: <회색 지대 항목>
```
순위는 "가장 냄새나는 것"이 아니라 "지금 고쳐서 가장 많이 얻는 것"(judgment.md).

## 악취 → 기법 빠른 참조 (부록 B)

| 악취 | 먼저 시도할 기법 → 그다음 |

| 기이한 이름 | 함수 선언 바꾸기, 변수 이름 바꾸기, 필드 이름 바꾸기 |
| 중복 코드 | 함수 추출하기 → 문장 슬라이드하기, 메서드 올리기 |

| 긴 매개변수 목록 | 매개변수를 질의 함수로, 객체 통째로 넘기기, 매개변수 객체, 플래그 인수 제거, 여러 함수를 클래스로 |

| 뒤엉킨 변경 | 단계 쪼개기, 함수 옮기기, 함수 추출, 클래스 추출 |
| 산탄총 수술 | 함수·필드 옮기기, 여러 함수를 클래스/변환 함수로, 단계 쪼개기, (일단 모으려면) 함수·클래스 인라인 |
| 기능 편애 | 함수 옮기기 (일부만이면 먼저 함수 추출) |
| 데이터 뭉치 | 클래스 추출 → 매개변수 객체, 객체 통째로 넘기기 |
| 기본형 집착 | 기본형을 객체로 → 타입 코드를 서브클래스로 + 다형성, 클래스 추출, 매개변수 객체 |

| 반복문 | 반복문을 파이프라인으로 |
| 성의 없는 요소 | 함수 인라인, 클래스 인라인, 계층 합치기 |
| 추측성 일반화 | 계층 합치기, 함수·클래스 인라인, 함수 선언 바꾸기(매개변수 제거), 죽은 코드 제거 |
| 임시 필드 | 클래스 추출, 함수 옮기기, 특이 케이스 추가 |
| 메시지 체인 | 위임 숨기기 / 함수 추출 + 함수 옮기기 |
| 중개자 | 중개자 제거, 함수 인라인, 슈퍼/서브클래스를 위임으로 |
| 내부자 거래 | 함수·필드 옮기기, 위임 숨기기, 서브/슈퍼클래스를 위임으로 |
| 거대한 클래스 | 클래스 추출, 슈퍼클래스 추출, 타입 코드를 서브클래스로 |
| 다른 인터페이스의 대안 클래스들 | 함수 선언 바꾸기, 함수 옮기기, 슈퍼클래스 추출 |

## 하지 말 것

- 리팩터링 커밋에 동작 변경(버그 수정, 기능 추가, 출력 형식 변경) 섞기
- 테스트 없이 여러 파일에 걸친 큰 재구성 한 번에 하기 · 스냅샷 일괄 갱신 · 테스트를 "리팩터링에 맞춰" 고치기
- 죽은 코드를 주석 처리로 남기기 (버전 관리가 기억한다 — 지운다)
- "나중에 쓸지도 몰라서" 매개변수·추상 클래스·인터페이스 추가하기
- 텍스트 검색·치환으로 이름 바꾸기 (AST 기반 도구 또는 참조를 하나씩 확인)
- 단순한 조건문까지 다형성으로, 짧은 메시지 체인까지 숨기기, 한 줄 함수 수십 개 — 악취는 "살펴보라"는 신호이지 "무조건 고쳐라"가 아니다
- 사용자가 요청하지 않은 영역까지 정리 범위를 넓히기 (쓰레기 줍기는 지금 지나가는 길에서만)

## 완료 보고 형식

- **발견한 악취**와 위치
- **적용한 기법**(한국어 + English)과 순서, 커밋 단위
- **겉보기 동작 변경 없음의 근거** — 테스트 명령과 결과, 타입체크, diff에서 순수 이동이 아닌 줄이 있었다면 그 설명
- 리팩터링 중 발견했지만 **손대지 않은 것** (버그 의심, 다음 리팩터링 후보, 회색 지대 결정 요청)
