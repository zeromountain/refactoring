# 대규모 변경 패턴 (Large-Scale Change)

책 2.4 "오래 걸리는 리팩터링"과 2.5 "브랜치·데이터베이스" 논의를 실행 가능한 패턴으로 확장한 것.
근거: martinfowler.com bliki — Parallel Change (Danilo Sato, 2014), Branch By Abstraction (2014),
Strangler Fig (2024). 공통 원칙은 하나다: **시스템이 항상 동작하는 상태를 유지하며 조금씩 옮긴다.**
몇 주짜리 리팩터링 브랜치는 만들지 않는다(2.5) — 통합 시 충돌이 리팩터링 자체보다 비싸진다.

## 1. 병렬 변경 (Parallel Change / Expand–Migrate–Contract)

인터페이스를 **호환되지 않게** 바꿔야 할 때(시그니처 변경, 데이터 뭉치 → 값 객체, 필드 이름·타입 변경). 함수 선언 바꾸기(6.5)의 마이그레이션 절차를 일반화한 것.

1. **확장(expand)**: 옛 인터페이스를 **그대로 두고** 새 인터페이스를 옆에 추가한다. 내부적으로 둘 다 지원(옛 것이 새 것을 호출하거나, 잠시 두 자료구조 병행).
2. **이전(migrate)**: 호출자를 하나씩 새 인터페이스로 옮긴다. 각 이전은 독립 커밋·독립 배포 가능. 외부 클라이언트가 있으면 이 단계가 가장 길다(deprecated 표시, 사용량 로그로 잔여 호출자 추적).
3. **축소(contract)**: 호출자가 0이 되면 옛 인터페이스와 그것만 쓰던 내부 구조를 제거한다. 새 것의 임시 이름(`newCells`)을 원래 이름으로 되돌린다.

- 세 단계 어느 지점에서도 릴리스할 수 있다는 점이 핵심(지속적 배포와 호환).
- 확장 단계에서 두 구조를 병행할 때 **두 곳에 기록(dual write)** 하면 일관성 검증 어서션(10.6)을 넣어 둔다.

## 2. 추상화로 갈아타기 (Branch by Abstraction)

라이브러리·프레임워크·하위 시스템(ORM, HTTP 클라이언트, 템플릿 엔진)을 **교체**할 때. 버전 관리 브랜치 대신 코드 안의 추상화 계층을 "브랜치"로 쓴다.

1. 클라이언트 코드와 현재 공급자 사이에 **추상화 계층**(인터페이스)을 만든다. 처음엔 현재 공급자에 위임만.
2. 클라이언트 코드를 한 부분씩 추상화 계층을 통하도록 옮긴다(함수 옮기기 8.1, 위임 숨기기 7.7). 이 과정에서 추상화 계층을 통한 테스트를 보강한다.
3. 모든 상호작용이 추상화 계층을 지나면, **새 공급자** 구현을 같은 인터페이스로 만든다.
4. 기능 플래그로 일부 클라이언트/환경부터 새 공급자로 전환. 두 구현의 결과를 비교하는 검증(shadow run)도 가능.
5. 옛 공급자 사용이 0이 되면 제거. 추상화 계층이 더 이상 필요 없으면 그것도 제거(중개자 3.18가 되지 않도록).

- 변형: 공급자를 하위 기능별로 나눠 한 조각씩 갈아탄다. 한 번에 전부 바꿔야만 하는 경우도 있다.
- 항상 빌드·테스트가 통과하는 상태 유지. 트렁크 기반 개발과 함께 쓰는 것이 전제.

## 3. 교살자 무화과 (Strangler Fig)

레거시 시스템 전체를 **점진적으로 대체**할 때(재작성 대신).

- 새 기능부터 레거시 **바깥**의 새 코드베이스에 만들고, 레거시의 동작을 조금씩 새 쪽으로 옮긴다. 요청 라우팅(프록시/파사드)이 어느 쪽으로 보낼지 결정한다.
- 레거시의 기존 동작 중 상당수는 실제로 필요하지 않다 — "똑같이 다시 만들기"는 낭비. 원하는 결과를 먼저 합의하고, 문제를 쪼개고, 조각을 하나씩 전달한다.
- 전환 중 두 시스템이 데이터를 공유하는 방식(동기화, 단일 진실 원천)을 미리 정한다.
- 리팩터링 카탈로그와의 관계: 각 조각을 옮길 때 안에서는 단계 쪼개기(6.11), 함수 옮기기(8.1), 특성화 테스트(`safety.md`)가 쓰인다. 교살자는 그 조각들을 조직하는 상위 패턴이다.

## 4. 데이터베이스 스키마 변경 (Expand/Contract)

책 2.5: 스키마 변경도 릴리스 여러 번에 걸친 병렬 변경으로.

컬럼 이름 변경 예시(`user_name` → `display_name`):
1. **확장**: 새 컬럼 추가. 애플리케이션은 **양쪽에 기록**, 읽기는 옛 컬럼. 백필 마이그레이션으로 기존 행 복사.
2. **이전**: 읽기를 새 컬럼으로 전환(기능 플래그). 두 컬럼 값이 같은지 검증 쿼리/어서션.
3. **축소**: 옛 컬럼 기록 중단 → 다음 릴리스에서 컬럼 삭제.

- 각 단계는 독립 배포·롤백 가능해야 한다. "코드 배포와 마이그레이션이 동시에 성공해야만 동작하는" 변경은 만들지 않는다.
- 필드 이름 바꾸기(9.2)를 코드 안에서 하더라도 **직렬화 이름(컬럼·JSON 키)은 매핑으로 유지**하고 스키마는 별도 절차로 바꾼다.

## 5. 장기 리팩터링 운영 방식 (책 2.4)

- 팀 전체가 합의한 방향("이 라이브러리를 걷어낸다", "이 모듈을 나눈다")을 두고, **각자 그 코드를 지날 때마다 조금씩** 그 방향으로 옮긴다.
- 별도 "리팩터링 스프린트"보다 효과적이다. 대신 방향과 현재 진행 상태를 문서(ADR, `TODO` 목록, 남은 호출자 수)로 공유한다.
- 진척을 측정 가능하게: 옛 API 호출 수, 레거시 모듈 import 수, 추상화 계층 미경유 접근 수. 0이 되면 축소 단계.

## 6. 에이전트가 이 패턴을 만났을 때

- 요청이 "X를 Y로 교체", "이름을 전부 바꿔", "스키마 변경"처럼 **한 번에 끝낼 수 없는 규모**면, 위 패턴 중 하나로 **단계 계획**을 먼저 제시하고 첫 단계(확장 또는 추상화 계층 도입)만 수행한다.
- 확장 단계는 기존 동작을 바꾸지 않으므로 리팩터링이다. 이전 단계는 호출자별로 작은 리팩터링의 반복. 축소 단계는 죽은 코드 제거(8.9).
- 각 단계 사이에 배포가 끼어들 수 있다는 전제로 코드를 남긴다(옛 경로가 남아 있어도 깨지지 않게, 플래그 기본값은 옛 동작).
