# 판단 기준 (Judgment)

기법을 아는 것과 **무엇을 먼저, 어디까지, 언제 그만둘지** 아는 것은 다르다. 책에서 판단에 관한 문장들(2.4, 2.5, 3장 곳곳)을 모으고 실무 경험을 더했다.

## 무엇부터 손댈까 — 우선순위

1. **지금 하려는 변경을 막는 것** (준비 리팩터링 2.4). "이 기능을 넣기 쉽게 만드는 데 필요한 최소 변경"이 항상 1순위. 그 밖의 악취는 기록만.
2. **풀어주는 기법 먼저.** 이름 바꾸기·문장 슬라이드·변수 추출·함수 추출은 싸고 되돌리기 쉬우며, 뒤의 큰 기법(옮기기·다형성·클래스 추출)을 가능하게 한다. 큰 기법을 바로 시도해서 막히면 대개 이 준비가 부족한 것.
3. **자주 바뀌는 코드 > 안 바뀌는 코드.** `git log --since=6.months -- path`로 변경 빈도를 본다. 1년째 안 건드린 지저분한 코드는 후순위(2.4 "리팩터링하지 말아야 할 때").
4. **읽을 때마다 헷갈리는 것 > 그냥 못생긴 것.** 악취는 "이해 비용"으로 판단한다. 취향 차이(포맷, 스타일)는 악취가 아니다.
5. **위험이 낮은 것부터.** 순수 함수 안 → 클래스 안 → 모듈 경계 → 공개 API 순으로 위험이 커진다. 공개 API는 마이그레이션 절차(6.5) 필수.

## 언제 그만둘까

- 목표했던 변경이 쉬워졌으면 멈춘다. "이왕 손댄 김에"는 범위 확장의 시작이다.
- 다음 단계의 이름이 안 떠오르면 멈춘다. 이름이 없는 추출은 성의 없는 요소(3.14)를 만든다.
- 한 시간 넘게 초록을 못 보면 멈추고 되돌린다. 단계가 너무 크다는 신호.
- 리팩터링이 리뷰어가 읽을 수 없는 크기가 되면 멈추고 쪼개서 낸다. 리뷰 불가능한 리팩터링은 신뢰받지 못한다.
- 코드 소유자가 다른 영역(다른 팀 모듈)에 들어가야 하면 멈추고 조율한다(2.5 코드 소유권).

## 비용·효과 질문 세 가지

1. **이 코드를 다시 만질 것인가?** 아니라면 리팩터링의 회수 시점이 없다. 그대로 둔다.
2. **이 변경이 어떤 미래 변경을 쉽게 만드는가?** 구체적으로 답할 수 없으면 추측성 일반화(3.15)를 만들고 있을 가능성이 크다.
3. **되돌리기 비용은?** 이름 바꾸기·추출은 거의 0. 상속 계층 변경·모듈 경계 변경은 크다. 되돌리기 비용이 큰 기법은 확신이 클 때만.

## 과잉 리팩터링의 신호 — 리팩터링이 새 악취를 만들 때

| 신호 | 만들어진 악취 | 처방 |
|---|---|---|
| 한 줄짜리 함수가 수십 개, 이름은 `doStep1`, `helper2` | 성의 없는 요소(3.14), 기이한 이름(3.1) | 인라인(6.2)하고 의미 단위로 다시 추출 |
| 모든 클래스가 다른 클래스로 위임만 함 | 중개자(3.18) | 중개자 제거(7.8) |
| 인터페이스 하나에 구현체 하나, "나중에 바꿀 수 있게" | 추측성 일반화(3.15) | 계층 합치기(12.9), 인라인 |
| 매개변수 객체가 필드 하나짜리 | 성의 없는 요소 | 인라인 |
| 조건문 두 개를 클래스 네 개 + 팩터리로 | 추측성 일반화 | 반복되는 switch(3.12)가 아니면 조건문으로 되돌린다 |
| 값 객체가 데이터만 감싸고 동작이 하나도 없음 | 데이터 클래스(3.22) | 동작이 모일 때까지 기본형으로 두거나, 동작을 옮겨 온다 |
| diff의 절반이 포맷·import 순서·공백 | 리뷰 불가 | 포맷 변경을 별도 커밋으로 분리 |
| 테스트가 구현 세부(private 메서드 이름)에 결합됨 | 리팩터링을 막는 테스트 | 공개 동작 기준으로 테스트를 다시 쓴다 |

파울러: 간접 호출은 비용이다. 설명·공유·선택(다형성) 중 하나를 사지 못하는 간접 호출은 제거한다(6.2 배경).

## 자주 헷갈리는 선택

**클래스 추출(7.5) vs 슈퍼클래스 추출(12.8) vs 위임(12.10/12.11)**
- 두 클래스가 **같은 종류**이고 공통 부분이 크면 → 슈퍼클래스 추출. 처음엔 이게 가장 싸다(12.8 배경).
- 한 클래스 안에서 **일부 필드·메서드가 뭉쳐 다니면**(공통 접두사, 함께 변경) → 클래스 추출(구성).
- 이미 상속인데 **한 축 이상으로 분류**해야 하거나 부모 변경이 자식을 깨뜨리면 → 위임으로 전환.
- 확신이 없으면 상속으로 시작. 위임으로 바꾸는 절차가 있으니 나중에 바꿀 수 있다.

**함수 옮기기(8.1) 목적지가 애매할 때**
- 그 함수가 **데이터를 가장 많이 가져오는 모듈**로(3.9). 여러 모듈이 비슷하면 함수를 먼저 쪼개서(6.1) 각 조각을 따로 옮긴다.
- 옮겨 보고 나빠지면 되돌린다. 옮기기는 싸다.

**변수 추출(6.3) vs 함수 추출(6.1)**
- 이름이 그 함수 안에서만 의미 있으면 변수. 다른 곳에서도 쓸 법하면 함수. 클래스 안이면 메서드 쪽이 재사용에 유리.

**임시 변수를 질의 함수로(7.4) — 하지 말아야 할 때**
- 계산이 비싸고 여러 번 호출되며 실제로 측정된 병목일 때. 계산에 부작용이 있을 때(먼저 11.1).

**특이 케이스(10.5) vs 옵셔널/null 검사**
- null 검사가 **한두 곳**이면 그냥 검사. 같은 null 검사 + 같은 기본값이 **여러 곳**에 반복되면 특이 케이스 객체.

**다형성(10.4) vs 조건문 유지**
- 조건 분기가 **한 곳**이고 분기 수가 적으면 조건문. **같은 기준의 분기가 여러 곳**에 있거나 새 분기가 자주 추가되면 다형성.

**매직 리터럴(9.6) — 상수 vs 함수**
- 값으로 쓰이면 상수. 비교 대상으로 쓰이면(`x === 'M'`) 함수(`isMale(x)`).

## 진단 보고서에서 순위를 매기는 법

`SKILL.md`의 진단 모드에서 악취 목록의 순서는 다음 점수의 곱으로 정한다(대략).
- **빈도**: 이 악취가 몇 군데 반복되는가 (반복되는 switch 3곳 > 긴 함수 1개)
- **변경 빈도**: 그 코드가 최근 얼마나 자주 바뀌었는가
- **연쇄 가치**: 이걸 고치면 다른 악취도 풀리는가 (기이한 이름·기능 편애는 대개 다른 악취의 뿌리)
- **위험의 역수**: 고치는 데 필요한 변경 범위가 작을수록 앞으로

"가장 냄새가 심한 것"이 아니라 "지금 고쳐서 가장 많이 얻는 것"이 1번이다.
