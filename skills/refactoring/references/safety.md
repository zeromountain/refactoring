# 안전 프로토콜 (Safety Protocol)

책의 원칙(2장·4장)을 AI 에이전트가 실제 코드베이스에서 지키기 위한 구체적 절차. 리팩터링의 정의는
"겉보기 동작을 바꾸지 않는다"이고, 이 파일은 **그것을 어떻게 증명하느냐**에 대한 것이다.

## 시작 전 체크리스트

1. **작업 트리가 깨끗한가** — `git status`. 다른 변경이 섞여 있으면 사용자에게 알리고 어떻게 할지(커밋·스태시·그대로 진행) 묻는다. 사용자의 작업을 임의로 스태시하지 않는다. 리팩터링 diff는 리팩터링만 담아야 리뷰가 가능하다.
2. **테스트 명령을 아는가** — `package.json`/`Makefile`/`pyproject.toml`/CI 설정에서 찾는다. 전체 실행 시간도 확인한다(느리면 대상 모듈만 도는 명령을 따로 마련).
3. **테스트가 초록인가** — 빨간 테스트가 이미 있으면 그 테스트는 안전망이 아니다. 기록해 두고 무시하거나(리팩터링 대상과 무관할 때) 먼저 사용자에게 알린다.
4. **안전망이 실제로 잡는가** — 리팩터링 대상 코드에서 상수 하나를 바꾸거나 반환값을 뒤집어 테스트가 **빨개지는지** 확인하고 되돌린다. 통과만 하는 테스트는 아무것도 보장하지 않는다(4.2).
5. **커버리지가 없으면 특성화 테스트부터** (아래).

## 특성화 테스트 (Characterization Tests) — 테스트가 없을 때

Michael Feathers의 방법. 목적은 "올바른 동작"이 아니라 **"현재 동작"을 고정**하는 것이다.

1. 대상 함수를 호출하는 테스트를 쓴다. 기대값은 비워 두거나 명백히 틀린 값을 넣는다.
2. 실행해서 실제 출력을 얻는다.
3. 그 실제 출력을 기대값으로 붙여 넣는다. **알려진 버그가 있어도 그대로 고정한다** — 버그 수정은 다른 모자.
4. 입력을 바꿔 가며 반복: 정상 경로, 각 조건 분기, 경계값(빈 컬렉션, 0, 음수, null, 최댓값), 예외 경로.
5. 출력이 크면(리포트, HTML, JSON) **스냅샷/승인 테스트**(snapshot/approval)로 통째로 고정한다. 리팩터링 중에는 스냅샷 갱신을 하지 않는다 — 갱신이 필요하다면 동작이 바뀐 것이다.

**접합부(seam)** — 테스트 가능하게 만드는 최소 변경: 전역/싱글턴을 매개변수로 받게(질의 함수를 매개변수로 11.6), 시계·난수·I/O를 주입, 생성자에서 하는 무거운 초기화를 팩터리로(11.8). 이런 변경 자체는 안전한 리팩터링이어야 하고, 테스트 없이 하는 것이므로 **가장 작게**.

## 호출자 전부 찾기

이름 바꾸기·시그니처 변경·함수 옮기기의 실패 원인 대부분은 "호출자를 하나 놓침"이다.

- 1순위: **언어 서버/IDE 리팩터링** (rename, find references, extract). AST 기반이라 텍스트 검색보다 정확하다.
- 2순위: `grep -rn` 을 **여러 형태**로 — 함수 이름, 문자열 리터럴로 된 이름(`'methodName'`, `"methodName"`), 템플릿·설정 파일·마이그레이션·문서 안의 참조.
- grep이 놓치는 것들(수정 전에 반드시 의심): 리플렉션·동적 디스패치(`obj[name]()`, `getattr`, `send`), 문자열 키로 접근하는 필드(직렬화·ORM 컬럼·API 응답 필드·i18n 키), 데코레이터/어노테이션으로 등록되는 핸들러, 외부 패키지가 import 하는 공개 API, 테스트 더블의 메서드 이름.
- **공개 API**(다른 저장소·서비스가 호출)면 이름을 바꾸지 말고 **옛 이름을 위임 함수로 남기고 deprecated 표시**(6.5 마이그레이션 절차). 제거는 별도 릴리스에서.
- 필드 이름은 직렬화 형식(DB 컬럼, JSON 키, 이벤트 스키마)에 붙어 있을 수 있다. 그 경우 코드 안 이름만 바꾸고 직렬화 이름은 매핑으로 유지한다.

## 단계마다 증거 남기기

한 기법의 절차 한 단계 = 검증 한 번. "테스트"는 다음의 합이다.
- 테스트 스위트(대상 모듈만이라도 매번, 전체는 커밋 전)
- 타입 검사(`tsc --noEmit`, `mypy`, 컴파일) — 이름 바꾸기·시그니처 변경의 누락을 가장 빨리 잡는다
- 린트 — 미사용 import·변수는 죽은 코드 제거의 신호
- **diff 리뷰** — 커밋 전에 `git diff`를 읽고 "순수한 이동/이름 변경이 아닌 줄"이 있는지 찾는다. 있다면 그 줄이 동작을 바꾸지 않는 이유를 설명할 수 있어야 한다. 설명이 안 되면 되돌린다.

빨개지면 **디버깅하지 말고 되돌린다**. 되돌리는 범위는 **마지막 초록 이후 이 단계에서 건드린 파일·줄만**이다 — 커밋하지 않고 진행 중이면 특성화 테스트와 앞선 단계들도 같은 작업 트리에 있으므로 `git checkout -- .`·`git stash`처럼 트리 전체를 지우는 명령은 쓰지 않는다(파일 단위 `git checkout -- <file>`도 그 파일에 앞선 단계의 변경이 있으면 안 된다). 마지막 초록 상태에서 더 작은 단계로 다시 시도한다. 되돌리기가 디버깅보다 거의 항상 싸다(2.1: "리팩터링 중 시스템이 몇 분 이상 깨져 있으면 안 된다").

## 커밋 단위

커밋은 **사용자가 원할 때만** 한다(SKILL.md 절차 4). 시작 전에 커밋 여부를 한 번 확인하고, 확인하지 않았거나 "커밋은 내가 한다"면 아래의 "커밋"은 **"검증이 끝난 단계 경계"**로 읽는다 — 변경만 남기고 단계 경계를 보고서에 적는다.

- 기법 하나(또는 같은 기법을 여러 곳에 적용한 묶음) = 커밋 하나. 메시지에 기법 이름: `refactor: 조건부 로직을 다형성으로 — Pricing`.
- 포맷터가 파일 전체를 바꾸면 그 변경을 **별도 커밋**으로 먼저 분리한다. 리팩터링 diff에 공백 변경이 섞이면 리뷰가 불가능해진다.
- 리팩터링 커밋과 동작 변경 커밋을 섞지 않는다. 리팩터링 도중 버그를 발견하면: 메모 → 리팩터링 완료·커밋 → 버그 재현 테스트 → 수정 → 별도 커밋.

## 동작이 바뀌는 회색 지대 — 사용자에게 먼저 묻는다

다음은 "리팩터링"으로 보이지만 겉보기 동작을 바꿀 수 있다. 하기 전에 알리고 동의를 받는다.
- 평가 순서·횟수 변경(반복문 쪼개기로 부작용 있는 호출이 두 번 실행, 지연 평가 → 즉시 평가)
- 부동소수점 연산 순서 변경(합계 계산을 reduce로 바꿀 때 반올림 차이)
- 예외 타입·메시지 변경, 오류 코드 → 예외(호출자의 catch 로직이 달라짐)
- 컬렉션 캡슐화로 복제본을 반환하면서 호출자가 기대하던 참조 동일성이 깨짐
- 값 객체 도입으로 `===` 비교가 실패하게 됨
- 로그·메트릭 문자열 변경(운영 대시보드가 파싱하고 있을 수 있음)
- 공개 API·직렬화 형식의 이름 변경

## 하지 말아야 할 "안전해 보이는" 것

- 리팩터링 도구 없이 프로젝트 전체 `sed`/치환으로 이름 바꾸기
- 테스트를 "리팩터링에 맞춰" 고치기 — 테스트가 인터페이스 변경 때문에 깨진 것(호출 형태만 변경)과 동작 변경 때문에 깨진 것을 구분한다. 후자면 리팩터링이 아니다.
- 스냅샷 일괄 갱신
- "어차피 안 쓰는 것 같아서" 참조 확인 없이 코드 삭제
- 여러 파일에 걸친 큰 변경을 한 번에 하고 마지막에 테스트
